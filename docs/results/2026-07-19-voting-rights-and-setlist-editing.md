# 투표권·다른 버전·셋리스트 편집 구현 결과

기준: `CONTEXT.md`, `docs/adr/0001`~`0007`, `docs/plans/2026-07-19-voting-rights-and-setlist-editing.md`.

## 구현 결과

- 신규 합주방 생성 시 자유 투표와 투표권 할당을 선택하고, 할당 모드의 기본값을 1~99로 입력한다.
- 로그인 참여자를 첫 방문에 자동 등록하고 방장도 생성과 동시에 등록한다.
- 투표권 차감·방향 변경·취소·초과 검사를 한 DB 트랜잭션에서 처리한다. 방장도 같은 제한을 받는다.
- 방장 톱니바퀴에서 투표 전 모드 변경, 미래 참여자 기본값, 현재 참여자 개별값과 명시적 일괄 적용을 관리한다.
- 후보곡 삭제는 로그인 합주방의 방장 또는 등록자에게 허용하고, 옛 익명 합주방은 방장 토큰만 허용한다.
- 후보곡마다 YouTube 다른 버전 링크, 자동 제목·썸네일, 100자 설명과 별도 개수 아이콘을 제공한다.
- 중복 링크는 원본/기등록 링크를 구분해 경고하고 사용자가 확인하면 저장한다.
- 셋리스트는 기본 모두 편집이며, 방장이 추가·수정·초기화·순서·삭제 전체를 방장 전용으로 전환할 수 있다.
- 인터벌은 이름·설명·분·초를 생성·수정하고, 곡 블록은 원본을 보존한 채 셋리스트 전용 제목·시간을 수정·초기화한다.
- 상단은 인터벌을 제외한 `N곡 · 토탈 시간 · N곡 시간 미입력`을 표시한다.
- 인터벌 설명은 화면에서 접고 펼친 상태를 현재 페이지 동안 유지한다. PDF에는 전체 항목을, 공유 이미지에는 공간에 들어가는 설명을 전부 표시한다.
- 셋리스트 캘린더, ICS API, 포스터 UI·Action·OG 합성·이미지 허용 설정을 제거했다.

## 삭제 버그 진단

사용자가 방장인데 삭제 버튼을 눌러도 아무 반응이 없던 직접 원인은 `SongCard` 삭제 핸들러의 `if (!adminToken) return`이었다. 로그인 계정으로 방장임을 증명할 수 있어도 브라우저 토큰이 아직 없으면 서버 호출과 오류 알림 전에 조용히 종료됐다.

이 조기 종료를 제거하고, 버튼 노출은 방장 또는 등록자 ID로, 최종 허용은 Server Action에서 현재 계정과 DB의 방장·등록자 ID로 판정하도록 바꿨다. 컴포넌트 회귀 테스트는 토큰이 없는 로그인 방장·등록자의 삭제 요청 도달과 다른 참여자의 버튼 미노출을 검증한다.

## 포스터 영구 삭제 결과

- 변경 전 `setlist-posters` 버킷의 루트 항목 1개를 확인했다.
- Supabase Storage API로 실제 파일을 비우고 버킷을 영구 삭제했다.
- `poster_url` 값이 남은 합주방 1개를 `NULL`로 정리했다.
- 재확인 결과 버킷 없음, `poster_url` 값 0개다.
- 이 작업은 복구할 수 없다. `poster_url` 컬럼 자체는 v10 SQL 적용 시 제거된다.

`storage.objects`를 SQL로 직접 지우면 실제 파일이 고아 객체로 남을 수 있어, 재실행 가능한 `scripts/remove-setlist-posters.mjs`를 운영 도구로 추가했다.

## 구현 중 적용한 권장 판단

- 기본 투표권은 3표로 정했다. DB·생성 화면·설정 화면의 초기값을 동일하게 맞췄다.
- 할당 모드는 안정적인 계정 식별자가 있는 신규 로그인 합주방에만 제공하고, 기존 익명 합주방은 자유 투표를 유지한다.
- `모두 편집`인 로그인 합주방은 자동 등록된 참여자만 서버에서 허용한다. 기존 익명 합주방은 과거 링크 공동 편집 동작을 유지한다.
- 투표권 초과는 UI 선검사 대신 참여자 행 잠금을 사용하는 DB 함수에서 최종 보장한다. 방향 변경은 새 표를 만들지 않아 추가 차감하지 않는다.
- 공유 이미지는 설명이 있는 인터벌을 세로 공간 3단위, 일반 항목을 1단위로 계산해 한 장에 들어가는 항목까지만 전체 표시하고 나머지를 `외 N개 항목 더`로 표시한다.
- 모바일 셋리스트의 네 편집 동작은 곡 정보 아래 두 번째 줄로 배치해 44px 터치 영역을 지키고 좁은 화면의 가로 넘침을 피했다.
- 셋리스트 변경 실패 시 낙관적 화면 상태를 원래 순서·목록으로 되돌리고 실제 오류 문구를 알린다.

## 데이터베이스 적용 순서

1. 배포 전에 Supabase SQL Editor에서 `supabase-migration-v10.sql`을 실행한다.
2. 신규 컬럼·테이블·함수·RLS 정책 생성과 `poster_url` 컬럼 제거를 확인한다.
3. 애플리케이션을 배포한다.
4. 자유/할당 합주방을 각각 하나 만들고 투표, 다른 버전, 셋리스트 편집 토글을 도그푸딩한다.

Storage 파일과 기존 URL 값 정리는 이미 완료했으며, v10 SQL 적용 전에는 새 코드의 신규 기능을 배포하면 안 된다.

## 자동 검증

- `npm test`: 3개 파일, 9개 테스트 통과
- `npm run typecheck`: 통과
- `npm run lint`: 통과
- `npm run build`: Next.js 16.2.1 프로덕션 빌드 통과
- `git diff --check`: 통과
- 디버그 로그 `[DEBUG-*]`: 잔여 없음
- `npm audit --omit=dev`: 기존 Next.js/PostCSS/ws 계열 3건(중간 1, 높음 2) 보고. 자동 수정은 Next 16.2.10 강제 변경을 포함해 이번 기능 범위에서는 적용하지 않았다.

자동 테스트는 셋리스트 수정값 우선·원본 보존·인터벌 합산·곡만 집계·미입력 시간, 투표권 범위와 사용량 미만 축소 거부, 곡 삭제 버튼 권한과 토큰 없는 로그인 방장 경로를 검증한다.

## 외부 적용 상태

코드와 운영 포스터 정리는 완료됐다. 데이터베이스 스키마 v10은 저장소에 준비됐지만 Supabase SQL Editor 실행 권한/연결 경로가 현재 작업 환경에 없어 아직 운영 DB에는 적용하지 않았다. 배포의 유일한 선행 작업은 위 v10 SQL 실행이다.
