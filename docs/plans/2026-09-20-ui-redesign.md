## 1. "AI티"의 정체

사용자가 말한 "AI티"를 여섯 가지로 쪼갰다. 전부 스크린샷이나 코드에서 확인한 것이다.

### 1-1. 모든 요소가 같은 목소리로 말한다

**관찰** (`final-mobile.png`, 375×812)

- 상단 240px 안에서 정렬축이 네 번 바뀐다.
  제목(좌) → 초대 배너(좌+우) → "5명 참여"(**중앙**) → "34곡 / 결과 공유"(좌) + 뷰 토글(우)
- `34곡`이 220px 간격으로 두 번 나온다. 헤더 부제(`PlaylistHeader.tsx:108`)와
  리스트 헤더(`PlaylistClient.tsx:434`).
- 곡 카드 안에서 가장 큰 활자는 **점수**다. 제목 14px/semibold, 채널 12px, 점수 18px/bold
  (`VoteButtons.tsx:69` `font-bold text-lg`). 이 화면의 주인공은 곡인데 숫자가 이긴다.

**왜 AI처럼 보이나**: 생성 모델은 "필요한 정보를 다 넣는" 쪽으로 기운다.
사람 디자이너는 무엇을 **버릴지** 먼저 정한다. 버려진 게 하나도 없는 화면은 티가 난다.

### 1-2. 근거 없는 형태 다양성 — 라디우스 6종

**관찰** (`src/**/*.tsx` 전수)

| 클래스 | 사용 횟수 |
|---|---|
| `rounded-xl` | 91 |
| `rounded-lg` | 60 |
| `rounded-full` | 46 |
| `rounded-2xl` | 24 |
| `rounded-md` | 10 |
| `rounded-3xl` | 1 |

규칙이 없다. `Card` primitive는 `rounded-2xl`인데, 실제 곡 카드는 `rounded-xl`
(`SongCard.tsx:111`), 셋리스트 행도 `rounded-xl`, 합주 카드도 `rounded-xl`이다.
카드 하나 안에서도 썸네일 `rounded-lg`, 댓글 뱃지 `rounded-md`, 댓글 수 `rounded-full`로 갈린다.

**왜**: 형태가 의미를 담지 않고 "그때그때 어울려 보이는 값"으로 골라져 있다.
이게 화면을 볼 때 "뭔가 조립된 느낌"으로 읽힌다.

### 1-3. 디자인 시스템이 선언만 되고 쓰이지 않는다

**관찰**

- `src/components/ui/Card.tsx`를 **import하는 파일이 0개**다. `Input.tsx`도 **0개**다.
  `Button`은 2개 파일(`HeroCTA`, `VotingSettingsButton`)에서만 쓴다.
  대신 원시 `<button>`이 `SongCard` 14개, `DeadlinePicker` 13개, `CreatePlaylistForm` 11개,
  `FilterBar` 9개… 로 흩어져 있다. `Toast.tsx`도 어디서도 import하지 않는다.
- 타이포 토큰이 있는데 raw Tailwind 사이즈가 97회 쓰인다.
  `text-xs` 46, `text-lg` 25, `text-xl` 11, `text-2xl` 6, `text-base` 5, `text-3xl` 3, `text-4xl` 1.
- `text-xs`(12px / 행간 16px, Tailwind 기본값)와 `text-caption`(12px / 행간 18px, 프로젝트 토큰)은
  **같은 크기에 다른 행간**인데 각각 46회·88회 혼용된다.
- `text-lg`(18px)는 토큰 스케일에 **없는 크기**다. `text-body`(16px)와 `text-h3`(20px) 사이를
  25곳에서 메우고 있다.
- **`bg-warning-soft`가 3곳에서 쓰이는데 `--color-warning-soft`가 `globals.css`에 정의돼 있지 않다.**
  → `SongCard.tsx:178`, `SongCard.tsx:339`, `VoteAllowanceStatus.tsx:13`의 배경색이 실제로 안 나온다.
- 직접 색상이 33회 남아 있다. `text-red-400` 8, `bg-red-600` 4, yellow 계열이 10가지 음영으로 17회.
  `--color-warning`이 있는데 `text-yellow-400`, `border-yellow-600/50`을 쓴다.

**왜**: `AGENTS.md`가 "새 컴포넌트는 primitives 위에 쌓을 것, 인라인 클래스 복붙 X"라고
적어놨는데 코드가 정확히 그 반대다. **규칙 문서와 코드가 따로 노는 상태**가 AI 생성물의 특징이다.
사람이 쌓아올린 코드베이스는 규칙이 적힌 순간부터 지켜지거나, 안 지킬 거면 규칙이 지워진다.

### 1-4. 장식이 정보보다 눈에 띈다

**관찰**

- 합주방 헤더에서 가장 밝은 요소는 카카오 노란색 `#FEE500` 버튼이다(`PlaylistHeader.tsx:124`).
  이 화면의 주 행동은 투표인데, 공유 버튼이 시각적 1순위를 가져간다.
- 하단 탭이 컬러 이모지다. `🎵 플레이리스트 / 📋 셋리스트 / 🎸 합주` (`NavigationBar.tsx:11-13`).
  다크 플랫 UI 위에 애플 컬러 이모지가 얹히면 해상도·채도·광원이 전부 어긋난다.
- 홈 통계 줄에 `✨` + `text-neon`(text-shadow 2겹), 플로팅 음표 3개(opacity 0.06~0.10).

**왜**: 이모지와 글로우는 "성의"의 대체재로 쓰인다. 그리고 밴드 씬의 물성
(합주실, 앰프, 손으로 쓴 셋리스트 종이, 케이블)과 아무 관계가 없다.
장르에 소속되지 않은 장식은 항상 붕 뜬다.

### 1-5. 상태가 색으로만 구분된다

**관찰**

- 리스트/카드 뷰 토글: 트랙이 `bg-surface-hover`, 활성 버튼도 `bg-surface-hover`다
  (`PlaylistClient.tsx:443, 447, 458`). **선택된 칸의 배경 대비가 0이다.**
  아이콘 색(`text-white` vs `text-text-muted`) 차이만 남는다. 캡처에서도 구분이 거의 안 된다.
- 내 표 표시는 `text-upvote bg-upvote/10`, 10% 틴트뿐이다(`VoteButtons.tsx:52`).
- 점수 색은 부호로만 정해진다(`score > 0` 초록). "내가 찬성했다"와 "남들이 찬성했다"가 같은 초록이다.

**왜**: 색만으로 상태를 말하면 화면이 "칠해진" 느낌만 남고 구조가 안 읽힌다.
형태·위치·두께가 함께 움직여야 상태가 보인다.

### 1-6. 모든 간격이 12px다

**관찰** (`PlaylistClient.tsx:244~470`)

```
mt-3 보관 배너 → mt-3 초대 배너 → mt-3 참여자 줄 → mt-3 설정 버튼 →
VoteAllowanceStatus → mt-6 곡 추가 → mt-5 결과 배너 → mt-5 뷰 토글 → mt-3 목록
```

관계가 전혀 다른 블록들이 같은 12px로 붙어 있다.

**왜**: 간격은 "무엇과 무엇이 한 덩어리인가"를 말하는 언어다. 전부 같으면 아무 말도 안 하는 것과 같다.
이게 사용자가 느낀 "여백 리듬이 없다"의 실체다.

### 짚고 넘어갈 것 — 스크린샷 아티팩트

## 2. 화면별 리뉴얼 방향

우선순위: 합주방(투표) → 셋리스트 → 합주 모드 → 합주방 생성 → 홈.

근거: 합주방은 (a) 초대받은 멤버가 처음 착지하는 화면이고 (b) 체류 시간이 가장 길고
(c) 카톡 공유 링크가 가리키는 곳이다. 여기가 바이럴 루프의 입구다.

---

### A. 합주방 (투표) — P0

#### 현재 문제

**관찰**

1. 첫 곡 카드 상단이 화면 위에서 약 240px 지점이다. 812px의 30%를 머리말이 쓴다.
   한 화면에 곡이 3개 들어간다.
2. 헤더 아이콘 3개가 40×40px다. `p-2.5`(10px) + `w-5`(20px) = 40.
   `AGENTS.md`의 ≥44px 규칙 위반.
3. "결과 공유"가 `text-xs text-text-subtle` 텍스트 링크다(`PlaylistClient.tsx:438`).
   패딩도 `min-h`도 없다. **카톡 공유가 코어 루프인데 화면에서 가장 약한 요소다.**
4. 아티스트 자리에 YouTube 채널명이 그대로 들어간다.
   `YOUNHA - Topic`, `kwon.orca.archive`, `Mnet TV`,
   `Pop music crooners of the 20th century`(이건 채널 설명이지 아티스트도 아니다).
5. 뷰 토글 활성 상태가 안 보인다 (1-5 참고).
6. 기명 모드에서 투표자 줄이 모든 행에 깔린다 (백로그 6번과 동일 관찰).

#### 방향

**한 화면에 곡만 보이게 한다. 점수를 "곡의 속성"이 아니라 "순위"로 읽히게 만든다.**

#### 구체안

- **A-1. 헤더 1줄화.** 제목 + 아이콘만. 부제 `34곡` 삭제(리스트 헤더와 중복).
  아이콘 버튼 `p-2.5` → `h-11 w-11 flex items-center justify-center`.
- **A-2. 메타 한 줄 통합.** 지금 세 군데로 흩어진 정보
  (초대 배너 / `5명 참여 | 마감 | ...으로 참여 중` 줄 / 로그인 버튼)를
  헤더 바로 아래 12px 한 줄로 합친다.
  `5명 참여 · 마감 D-2 · 이요셉으로 참여 중` + 우측에 로그인 버튼(비로그인일 때만).
- **A-3. 카카오 노란 버튼을 헤더에서 뺀다.**
  헤더에는 무채색 공유 아이콘만 둔다. 노란색은 **공유가 실제로 다음 행동인 순간**에만 쓴다:
  곡이 0~2개일 때, 투표 마감 직후, 셋리스트 확정 직후. 그때는 전체 폭 버튼으로.
  → 이유: 노란색이 화면에서 유일하게 튀는 색이라 시선 예산을 통째로 쓴다.
  공유 총량을 줄이는 게 아니라 **타이밍을 옮기는** 것이다.
- **A-4. 순위를 보이게 한다.**
  - 1~3위 좌측에 `01 02 03` 넘버. 4위부터는 번호 없음.
  - 점수를 18px → 16px로 낮추고, 옆에 가느다란 막대(최고점 대비 비율)를 둔다.
    지금 `5 5 4 4 4 4`가 숫자로만 나와서 "박빙"인지 "압도적"인지가 안 읽힌다.
  - 동점 처리: 같은 점수면 같은 등수 표기.
- **A-5. 아티스트 필드 정제.**
  `- Topic` 접미사 제거 → 제목이 `A - B` 패턴이면 A를 아티스트로 승격 →
  채널명이 제목과 겹치거나 의미 없으면 **아예 숨긴다**. 빈 줄이 틀린 줄보다 낫다.
  (`src/lib/youtube-data.ts`에 순수 함수로 넣고 테스트)
- **A-6. 투표자 줄 접기.** 기본은 `▲ 김주현 외 4명`, 탭하면 펼침. (백로그 6번)
- **A-7. 뷰 토글 활성 대비 수정.** 활성 칸을 `bg-surface-elevated` + `border border-border-strong`로.

**예상 결과**: 첫 곡이 약 240px → 약 150px. 한 화면에 곡 3개 → 4~5개.

### B. 셋리스트 — P0

#### 현재 문제

**관찰** (`setlist-mobile.png`, `SetlistView.tsx`)

1. 곡 블록과 인터벌 블록이 **같은 카드 모양**이다. 7번 `정비시간 5:00`이 다른 점은
   썸네일 자리에 주황 시계 아이콘이 들어간 것뿐이다.
2. 시간이 행마다 `3:45`로만 있고 **누적 시간이 없다.** 공연 순서를 짤 때 알고 싶은 건
   "이 곡 끝나면 몇 분 지났나"다.
3. 상단 요약 `12곡 · 54:19`가 14px 텍스트로 왼쪽 구석에 있다. 이 화면에서 가장 중요한 숫자다.
4. 순서 변경이 ▲▼ 버튼이다. 12곡짜리에서 1번을 12번으로 옮기려면 탭 11번.
5. **순서 변경에 애니메이션이 없다.** `useAutoAnimate`은 `PlaylistClient.tsx:69`의
   투표 목록에만 걸려 있다. `SetlistView`의 `sortedItems.map`에는 없어서 행이 순간이동한다.

#### 방향

**리스트가 아니라 타임라인으로.** 셋리스트의 본질은 "순서"가 아니라 "시간표"다.

#### 구체안

- **B-1. 좌측 누적 시간 눈금.** 각 행 왼쪽에 `0:00 / 3:45 / 7:14 …`.
  번호는 그 아래 작게. `summarizeSetlist`가 이미 총합을 계산하므로 누적은 `reduce` 하나면 된다.
- **B-2. 인터벌을 카드가 아니라 틈으로.** 높이 32px, 상하 점선, 중앙에 `정비시간 · 5:00`.
  곡은 카드, 인터벌은 카드 사이의 **여백**. 형태가 의미를 갖는다.
- **B-3. 요약을 sticky 바로.** `12곡 · 54:19`를 `text-h3 tabular-nums`로 키우고
  공유 버튼과 같은 줄에 두고 스크롤해도 상단에 남긴다.
  `N곡 시간 미입력` 경고도 여기서.
- **B-4. 순서 변경.** 1차는 `useAutoAnimate` 추가만(한 줄). ▲▼가 보이게 움직인다.
  드래그는 별도 단계 — 아래 6단계에서 다룬다.
- **B-5. 빈 상태에 이동 수단.** 지금 "셋리스트가 비어있어요 / 투표 리스트에서 곡을 추가해보세요"인데
  가는 길이 없다. `상위 N곡 한 번에 넣기` 버튼 + 탭 전환 링크를 둔다.

### C. 합주 모드 — P1

#### 현재 문제

**관찰** (`rehearsal-mobile.png`)

12개 카드가 **전부 똑같다.** 썸네일 + 제목 + `+ 메타 추가 (키·BPM·난이도...)`.
실제 프로덕션 데이터에서 키·BPM이 **한 곡도 안 채워져 있다**(백로그 3번).
각 카드 아래 `CommentSection` 자리는 비어 있어서 카드마다 빈 영역이 남는다.

#### 진단

이 화면은 **"입력을 기다리는 빈 양식 12장"**이다.
합주실에서 악기 들고 폰을 볼 때 필요한 건 입력 폼이 아니라 "지금 몇 번째 곡이고 얼마 남았나"다.
백로그의 관찰 — 12곡 전부 메타 미입력 — 이 이 화면이 안 쓰인다는 증거다.

#### 방향

**입력 화면에서 진행 화면으로.**

#### 구체안

- **C-1. 한 번에 한 곡.** 현재 곡을 크게(제목 `text-h2`, 키·BPM·시간을 그 아래 큰 칩으로),
  다음 곡을 하단에 작게. 좌우 스와이프로 이동. 12장 스택을 버린다.
- **C-2. 상단 진행 바.** `3 / 12 · 남은 38:20`. 합주 시간 관리는 밴드의 실제 문제다.

## 3. 인터랙션 설계

원칙: **움직임은 상태 변화를 설명할 때만.**
지금 `animate-fade-in`이 19곳에서 "등장"에 쓰이는데, 등장은 설명할 게 없다.

### 3-1. 투표 피드백

현재: `active:scale-90` + `disabled:opacity-60`. 낙관적 업데이트라 숫자는 즉시 바뀐다.

추가안:

| 동작 | 표현 | 시간 |
|---|---|---|
| 화살표 탭 | 색 채워짐 + `scale 1 → 1.15 → 1` | 160ms |
| 점수 변경 | 숫자가 위/아래로 4px 밀려 교체 | 140ms |
| 순위 변동 | `useAutoAnimate`이 행 이동 (**이미 동작 중**) | 300ms |
| 순위 변동 강조 | 이동 끝난 뒤 좌측 보더 2px가 primary로 켜졌다 꺼짐 | 200ms, 120ms 지연 |
| 실패 롤백 | 숫자 원위치 + 행 배경 `bg-danger/8` | 300ms |

- 햅틱: `navigator.vibrate(10)`. Android만 동작하지만 비용이 0이다.
- 순위 변동 강조는 auto-animate의 이동과 **겹치지 않게** 지연을 준다. 동시에 일어나면 둘 다 안 보인다.

### 3-2. 셋리스트 구성

- `useAutoAnimate`을 `SetlistView` 목록에 추가. **한 줄**이고 효과가 가장 크다.
- 셋리스트 추가 확인 시트를 없앤다. 바로 추가 + 하단 토스트 `셋리스트에 추가했어요 · 되돌리기`.
  확인 다이얼로그는 되돌릴 수 없는 일에만 쓴다. (`Toast.tsx`가 이미 있는데 안 쓰이고 있다)
- 누적 시간은 카운트업하지 않고 즉시 교체. 움직임 예산은 순서 변경에 쓴다.

### 3-3. 곡 전환 / 재생

- 재생 중인 행 좌측에 3줄 이퀄라이저. **`@keyframes eq`가 `globals.css`에 이미 있다**
  (`DemoPlayback`, `DemoBand`에서만 쓰는 중). 실제 플레이어에 재사용.
- 지금 재생 중 표시는 썸네일 하단의 `animate-bounce` 막대 3개인데
  썸네일 위 `bg-black/30` 오버레이에 묻힌다. 행 좌측으로 꺼낸다.
- 독 펼침은 `max-h` 트랜지션 유지. **언마운트 금지 제약**(백로그 2번)을 깨면 안 된다.

### 3-4. 터치

**관찰 — 44px 미만인 곳**

| 위치 | 현재 크기 | 코드 |
|---|---|---|
| 합주방 헤더 아이콘 3개 | 40×40 | `PlaylistHeader.tsx:115,124,141` (`p-2.5` + `w-5`) |
| 플레이어 독 컨트롤 4개 | 32×32 | `MiniPlayer.tsx:72,87,117,128` (`p-2` + `w-4`) |
| 플레이어 재생/정지 | 40×40 | `MiniPlayer.tsx:100` (`p-2` + `w-6`) |
| 하단 탭 | 약 32 높이 | `NavigationBar.tsx:28` (`py-2` + `text-xs`) |
| 필터 칩 | 40 높이 | `FilterBar.tsx:80,94,126` (`h-10`) |
| 뷰 토글 | 28×28 | `PlaylistClient.tsx:446,457` (`p-1.5` + `w-4`) |

플레이어 독의 32px는 특히 문제다. **합주 중에 악기 들고 누르는 버튼**이다.

- 전부 44px 이상으로. 시각 크기는 유지하고 히트 영역만 키운다
  (`inline-flex h-11 w-11 items-center justify-center` + 아이콘은 그대로).
- 하단 탭 3개 사이를 **가로 스와이프**로도 이동. 한 손 조작 대응.

### 3-5. 접근성

- `prefers-reduced-motion`은 `globals.css`에서 전역 처리돼 있다.
  **새 애니메이션도 CSS `transition`/`animation`으로만 구현하면 자동 적용된다.**
  JS 기반 애니메이션(requestAnimationFrame 수동 보간)은 쓰지 않는다.
- 색으로만 구분되는 상태를 없앤다(1-5). 아이콘 채움/빈 형태를 함께 바꾼다.

### 4-3. 타이포

- **`--text-h4: 1.125rem` 추가** (line-height 1.5).
  `text-lg`가 25곳에서 이미 이 자리를 메우고 있다. 한국어 UI에서 16↔20 사이는 실제로 필요하다.
  스케일을 부정하지 말고 인정한다.

  `.nums { font-variant-numeric: tabular-nums; }` 한 줄로 통일. 점수가 흔들리지 않는다.

### 4-4. 컬러 역할 분리 (제안)

지금 `primary`(보라) 하나가 다음을 전부 겸한다:
브랜드 · 선택 상태 · 재생 중 · 링크 · 강조 숫자 · 뱃지 · 진행 바.
그래서 화면이 보라로 얼룩진다.

| 역할 | 지금 | 제안 |
|---|---|---|
| 행동 (버튼·링크) | primary | **primary 유지** |
| 재생 / 현재 곡 | primary | `accent-play` (시안) |
| 선택 상태 | `bg-primary` 채움 | `bg-surface-elevated` + `border-border-strong` |
| 찬성 / 반대 | success / danger | 유지 |

**이것 하나만으로 "칠해진 느낌"이 크게 준다.** 색을 더 쓰는 게 아니라 역할을 나누는 것이다.

### 4-5. primitives

`Card`와 `Input`은 import 0회다. 선택지는 (a) 실제로 쓰게 하거나 (b) 지우거나 둘 중 하나다.

**(a)를 택한다.** 단, 원인을 먼저 고친다:
현재 `Card`(`rounded-2xl p-4`)가 실제 쓰임(`rounded-xl p-3`)과 안 맞아서 안 쓰인 것이다.
Card를 실사용 값에 맞춰 조정한 뒤 `SongCard` / `SetlistView` / `RehearsalView`가 쓰게 한다.

새로 필요한 것:

- `IconButton` — 44px 고정. 위의 터치 영역 6종이 전부 이걸로 대체된다.
- `Chip` — 필터·메타·뱃지 공용. 지금 `FilterBar`에만 4가지 변형이 인라인으로 있다.
- `Sheet` — **불필요.** `Modal`이 이미 모바일 sheet 동작을 겸한다(`items-end sm:items-center`).

### 4-6. shadcn/ui 도입 — 하지 않는다

**비용**

- Radix 의존성 15개 내외 추가. 컴포넌트 소스가 프로젝트로 복사되므로 유지보수 대상 파일이 20~30개 늘어난다.
- shadcn은 자체 CSS 변수 체계(`--background`, `--foreground`, `--muted`, `--accent`)를 쓴다.
  지금 시맨틱 토큰(`--color-bg`, `--color-text-muted`, `--color-surface`)과 이름·구조가 다르다.
  둘을 공존시키면 토큰이 두 벌이 되고, 갈아엎으면 `AGENTS.md` 규약과 100곳 넘는 클래스가 바뀐다.
- Tailwind v4 + Next 16 조합에서 shadcn 설정이 아직 매끄럽지 않다.

**얻는 것**

Dialog / Popover / Select의 접근성. 그런데 이 앱에 Select는 거의 없고,
`Modal`은 이미 포털 + ESC + 스크롤 락 + safe-area를 처리한다.

**핵심**: 진짜 문제는 컴포넌트 라이브러리가 없는 게 아니라 **있는 primitives를 안 쓰는 것**이다
(1-3). 라이브러리를 바꿔도 같은 일이 반복된다.

**예외 — 별도 판단이 필요한 하나**: 셋리스트 드래그 정렬을 진지하게 할 거면
`@dnd-kit/core` + `@dnd-kit/sortable`은 고려할 만하다(번들 크기는 도입 시점에 실측할 것).
직접 구현하면 모바일에서 스크롤 제스처와의 충돌 처리에 시간이 많이 든다.
다만 **6단계로 미룬다.** ▲▼ + auto-animate로 먼저 살아보고 불편하면 그때 넣는다.

## 6. 측정

`src/lib/analytics.ts`의 `EventMap`에 추가한다 (`AGENTS.md` 규약: 타입 먼저 등록).

```ts
kakao_shared: {
  variant: "playlist" | "decided" | "setlist";
  placement: "header" | "result_banner" | "setlist" | "empty_state";  // 추가
};
setlist_reordered: { method: "arrow" | "drag" };
rehearsal_song_changed: { index: number };
```

- `kakao_shared.placement` → 1단계에서 공유 버튼을 옮긴 판단이 맞았는지.
- `setlist_reordered` → 6단계 드래그 도입 여부 판단 근거.
- `rehearsal_song_changed` → 4단계 합주 모드가 **합주 중에 실제로 쓰이는지**.
- 기존 `meta_edited`는 이미 있다. 4단계 이후 메타 입력이 늘었는지 바로 볼 수 있다.

## 7. 카톡 공유 카드 영향

`AGENTS.md` 원칙 2에 따라 각 단계가 공유 카드에 주는 영향을 적는다.

- **1단계**: 공유 진입점 이동. 카드 자체는 안 바뀐다.
- **3단계**: 셋리스트에 누적 시간이 생기면 `/api/setlist-image`에도 총 러닝타임을 넣을 수 있다.
  단톡방에서 "54분짜리 셋리스트"가 보이는 건 지금보다 확실히 낫다.
- **5단계**: 용어가 "합주방"으로 바뀌면 `/api/og`의 문구와
  `KakaoShareButton`의 description(`${songCount}곡 등록 · ${participantCount}명 참여 중`)도
  함께 맞춘다. 여기가 안 맞으면 링크를 타고 온 사람이 다른 서비스에 온 줄 안다.

## 8. 하지 않을 것

- **컴포넌트 라이브러리 교체** (4-6)
- **홈 리뉴얼을 먼저** — 유일하게 괜찮은 화면이고 전환율 리스크가 있다
- **다크/라이트 테마 전환** — 다크 단일로 충분하다. 토큰이 이미 다크 전제로 짜여 있고,
  라이트를 만들면 색 결정이 두 배가 된다
- **디자인 토큰 전면 재정의** — 기존 시맨틱 체계는 방향이 맞다. 구멍만 메운다
- **애니메이션 라이브러리 추가** — `@formkit/auto-animate`와 CSS transition으로 충분하다.
  Framer Motion은 번들 대비 얻는 게 없다
