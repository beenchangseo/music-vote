## 1. 진입점과 흐름

### E1. 처음 온 사람 (방장 후보)

```
홈(로그아웃 랜딩) ── "카카오로 시작하기" ──▶ 카카오 ──▶ /auth/callback?next=/new ──▶ /new 플레이리스트 만들기
                                                                                   │
                         완료 화면 "곡 추가하러 가기" ◀──────────────────────────────┘
                           (내 밴드가 있으면 "이 플레이리스트를 밴드에 넣을까요?")
                                      │
                                      ▼
                              /playlist/{code} ── 카톡으로 링크 공유 ──▶ E2
```

- 목적지 `/new` 는 `HeroCTA.tsx:23` 에 고정돼 있다. 밴드 여부를 보지 않는다
- 화면: L1-home(랜딩 첫 화면), L2-new(로그아웃이면 로그인 안내 카드)

### E2. 단톡방 플레이리스트 링크로 온 멤버

```
/playlist/{code} (로그아웃) ── 보기는 됨, 투표·곡 추가는 막힘 ── "로그인" 칩 ──▶ 카카오 ──▶ 같은 주소
      │
      └─ 로그인 상태로 열면 그 방의 참여자로 자동 등록(playlist_members, PlaylistClient.tsx:124)
```

- 바이럴 루프의 중심. 이 사람은 밴드를 모른 채 들어온다
- 화면: L3-playlist

### E3. 밴드 초대 링크로 온 멤버

```
/join/{inviteCode}
  ├─ 로그아웃: "카카오로 로그인하고 들어가기" (표시 쿠키) ──▶ 카카오 ──▶ /join/{code}?join=1 ──▶ 자동 가입 ──▶ /band/{id}?joined=1
  └─ 로그인:   "밴드 들어가기" ──▶ /band/{id}?joined=1
```

- 화면: L4-join(로그아웃), B3-join(로그인한 비멤버)

### E4. 돌아온 사람 (로그인 홈)

```
홈(로그인) ── "+ 새 플레이리스트" ──▶ 모달 "플레이리스트 만들기" (E1 과 같은 폼)
          ├─ 내 밴드 선반 (밴드가 있을 때만) ──▶ /band/{id}
          └─ 내 플레이리스트 목록 ──▶ /playlist/{code}
```

- 로그인 홈의 버튼은 "새 플레이리스트" 하나다. 새 밴드 버튼은 없다
- 밴드가 없으면 "내 밴드" 섹션 자체가 숨는다(`MyBands.tsx:12`). 처음 로그인한 사람은 밴드라는 말을 볼 일이 없다
- 화면: B1-home(처음 로그인), B2-home-create(모달), A1-home(밴드 owner: 내 밴드 선반 + 내 플레이리스트)

### E5. 밴드가 생기는 길 (전부 플레이리스트 안)

```
/playlist/{code} (방장)
  ├─ ⋮ 플레이리스트 메뉴 ─▶ 플레이리스트 설정 ─▶ "이 멤버로 밴드 만들기" ─▶ 밴드 이름 시트 ─▶ /band/{id}?created=1   (promote)
  ├─ 안내 카드 "밴드 이름 정하고 만들기"  ← 방장 · 밴드 없음 · 로그인 멤버 ≥ 2 일 때만 (PlaylistClient.tsx:119)  (promote)
  └─ 내 밴드가 있으면 "이 플레이리스트를 내 밴드에 넣기"                                                (attach)
/new 완료 화면 ─ 내 밴드가 있으면 "이 플레이리스트를 밴드에 넣을까요?"                                    (attach)
```

- 플레이리스트가 없는 사람은 밴드를 만들 수 없다. 두 번째 밴드도 플레이리스트를 하나 더 만들어야 생긴다
- 결정 근거: CEO-D4 "밴드는 합주방에서 '이 멤버로 밴드 만들기'로 올린다. 방 만들기 흐름은 그대로"
  (계획 문서 325행, 2026-10-04 승인), ADR 0014
- 화면: A3-menu(⋮ 메뉴는 "플레이리스트 설정"·"홈으로" 두 개), A4b-settings-no-band(설정 맨 위 "밴드" 영역), A4-settings(밴드 안 플레이리스트는 밴드 홈 링크)

### E6. 밴드 홈과 밴드에서 새 플레이리스트

```
/band/{id} (멤버) ── "새 플레이리스트" ──▶ /new?band={id} ──▶ 밴드 안에 생성 (band)
                 ├─ 멤버 초대 시트 (링크 복사 · 카톡 · 링크 새로 만들기)
                 ├─ 공연 날짜 · 멤버 목록(내보내기) · 밴드 나가기
                 └─ 지금 플레이리스트 · 우리가 했던 곡
/band/{id} (비멤버·로그아웃) ── 이름 + "밴드 멤버만 볼 수 있어요" (+ 로그인 버튼)
```

- 화면: L5-band(로그아웃), A5-band-home · A6-invite-sheet · A7-new-band

## 4. CEO 리뷰에서 정할 것

1. **로그인 직후 목적지.** `/new` 유지 / 밴드 유무로 나누기(있으면 홈·밴드 홈, 없으면 밴드 만들기로 이끌기) / 홈으로
2. **플레이리스트 없이 밴드 만들기.** 홈(또는 첫 화면)에서 빈 밴드를 만들고 초대 링크로 멤버를 모으는 길을 더할지. 더하면 CEO-D4 를 고친다
3. **로그인 홈의 첫 버튼.** 새 플레이리스트 / 새 밴드 / 둘 다. 밴드가 있는 사람과 없는 사람을 다르게 할지
4. **밴드 없이 플레이리스트만 쓰는 사람.** 한 번 투표하고 끝나는 쓰임을 계속 1급으로 둘지
5. **로그아웃 범위.** `global` 유지 / 이 기기만(`scope: 'local'`)
6. **밴드 만들기 유도 장치.** 어디에(홈 · 플레이리스트 · 만들기 완료 화면), 어떤 모양으로(닫을 수 있는 카드 · 팝업 · 시트),
   누구에게(밴드가 없는 기존 방장 · 처음 온 사람), 얼마나 자주(한 번 닫으면 끝 · 다시 뜨는 조건). 지금 안내 카드의 조건
   (로그인 멤버 ≥ 2)을 그대로 둘지도 같이 본다. 기존 결정: 디자인 리뷰에서 유도 카드는 해당 상태에서만 뜨고 닫으면 기억한다
7. **밴드에 없는 플레이리스트를 밴드에 넣는 길.** 설정 안에만 둘지, 플레이리스트 화면 겉(헤더 · 안내 카드)에 꺼낼지
8. **밴드가 여럿일 때 넣기 UI.** 밴드 수만큼 버튼(지금) / 밴드를 고르는 목록 시트 / owner 인 밴드만 보이기

CEO-D4 를 고를 때의 근거도 같이 본다. 밴드는 이미 같이 투표해 본 사람들로 만들어진다. 바이럴 루프는 플레이리스트 링크 공유(E2)다. 빈 밴드는 가치가 보이기 전에 초대 단계가 하나 더 붙는다.

### 0A. 전제

- **진짜 문제**: 밴드라는 단위가 제품 겉에 없다. 밴드는 플레이리스트 방장이 설정 두 단계 안에서만 만들 수 있고,
  로그인 홈·로그인 직후 화면은 밴드를 말하지 않는다(P1~P4·P7·P8). 그래서 2026-10-04 에 그린 10배 그림
  "밴드가 기본 단위인 Plypick"(이전 CEO 계획 10x Check)에 사용자가 닿는 길이 좁다
- **목표 결과**: 밴드를 하려는 방장이 찾지 않아도 밴드를 만들 수 있고, 밴드가 있는 사람은 밴드에서 시작한다.
  한 번 투표하고 끝나는 사람의 길(웨지)은 느려지지 않는다
- **아무것도 안 할 때 비용**: 밴드 기능이 숨은 채 6주 지표(외부 밴드 ≥ 5)를 맞는다. 지표가 미달해도
  "수요가 없어서인지 못 찾아서인지" 구분할 수 없다. 지금 외부 밴드 0 (배포 하루)
- **반대쪽 근거 (CEO-D4 가 지킨 것)**: 웨지는 투표이고 투표는 멤버가 있어야 성립한다(office-hours 설계 문서).
  빈 밴드는 가치가 보이기 전에 초대 단계가 하나 더 붙는다. 플레이리스트 멤버마다 밴드를 따로 만들면
  같은 밴드가 여러 개 생긴다(방에서 올리기는 방장 한 명이 만들어서 이 문제가 없다)
- **수요 숫자**: 실제 방장 6명 중 플레이리스트 2개 이상 만든 사람 1명. 반복 수요는 아직 얇다

**정보 구조 (로그인 홈, 위에서 아래)**

**상태 커버리지**

| 기능 | 로딩 | 빈 | 오류 | 성공 | 부분 |
|---|---|---|---|---|---|
| 새 밴드 시트 | 버튼 로딩 (기존) | 이름 비면 비활성 | 버튼 아래 문구 | 밴드 홈 + `?created=1` 배너 | — |

| 밴드 홈 넣기 시트 | 목록 로딩 필요 ← 설계 | 넣을 것 0 ← 설계 | 시트 안 문구 | 목록에서 빠지고 밴드 홈 갱신 | 여러 개 연속 넣기 ← 설계 |

- **여정**: 처음 온 방장은 "밴드 이름 → 단톡방에 초대"로 30초 안에 첫 가치(멤버가 들어오는 것)를 본다. 기존 방장은 홈 카드에서
  이미 같이 투표한 사람들을 밴드로 묶는다. 링크로 온 멤버의 여정은 바뀌지 않는다
- **AI 슬롭 위험**: "밴드를 만들어 보세요!" 류 일반 문구 금지. AGENTS.md 톤("~해요", 페르소나 용어)과 기존 바이올렛 토큰 유지(방장 피드백)
- **모바일**: 버튼 두 개가 한 줄일 때 각각 ≥ 44px. 홈 카드는 닫기 버튼 44px (기존 `BandPromptCard` 와 같음)
- **접근성**: 시트는 `Modal` 의 포커스 트랩·복귀(T17) 그대로
- **GAP (승인 범위 안의 필수 수리)**: `getMyTeams` 는 조회 실패 때 `[]` 를 돌려주고(`team.ts:709-711`), `getMyPlaylists` 도 실패한

  밴드 만들기가 앞에 뜨고 중복 밴드가 생길 수 있다. CEO2-A 가 승인한 대상은 *정말로* 0/0 인 사람이므로, 구현 owner 가 증명할 것:

- 판정: 미정 설계 4건(로딩 · 넣을 것 0 · 연속 넣기 · 카드 대상 고르기)과 조회 실패 화면은 다음 `/plan-design-review` 로. Consider running /plan-design-review for a deep design review of this plan before implementation.
